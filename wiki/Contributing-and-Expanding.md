# Contributing & Expanding

This page is for developers who want to change MacSurf — fix a bug, add a CSS property, port another library, or wire in a new subsystem — without breaking the parts that already work. It assumes you've read [Architecture Overview](Architecture-Overview) and have a build going (see [Building MacSurf](Building-MacSurf)). The platform is unusual, so a lot of the advice here is "here's the trap, here's the way around it" rather than abstract style guidance.

A note up front, because it shapes everything: MacSurf is a solo, nights-and-weekends project. The maintainer is happy to review good patches and answer real questions, but there's no SLA, no 1:1 build hand-holding, and the supported way to get a working build is the StuffIt build pack, not a fresh `git clone`. None of that is meant to keep you out — it's meant to set honest expectations. Documentation fixes, compatibility reports, and well-scoped code changes are genuinely welcome.

## Before you write code

Two reflexes will save you the most time on this codebase.

The first is to **syntax-check on Linux before you touch the Mac.** CodeWarrior 8 compiles in strict C89, and the round trip from "edit a file" to "find out CodeWarrior hates it" is slow if it runs through a build on real hardware every time. The [Cross-Developing from Linux](Cross-Developing-from-Linux) workflow exists precisely so you catch C89 violations, missing includes, and bad pointer types in seconds on Linux. Run both the Retro68 PowerPC GCC pass and the plain `gcc -std=c89 -pedantic` pass with the shim include paths before you move anything over.

The second is to **grep the codebase before you build anything new.** MacSurf inherits the full NetSurf engine, which already has an image cache, a scheduler, option storage, and a lot more. The maintainer has reinvented wheels that NetSurf core already shipped more than once, so the standing advice is: check NetSurf core (and the RISC OS / Amiga / Atari frontends, which solved many of the same cooperative-multitasking problems) before assuming you need new infrastructure.

The hard constraints — strict C89, Carbon-only, cooperative multitasking only, the 16 MB partition budget — are spelled out in [`CONTRIBUTING.md`](https://github.com/mplsllc/macsurf/blob/master/CONTRIBUTING.md) and exhaustively in [CodeWarrior 8 & C89 Gotchas](CodeWarrior-8-and-C89-Gotchas). They aren't preferences. Code that violates them won't compile, or worse, will compile and crash on hardware in a way that's miserable to debug.

## Adding a CSS property, end to end

This is the single most common kind of expansion, so let's walk it end to end — the pipeline has a lot of stages, and skipping one produces silent failures rather than clean errors. MacSurf renders CSS natively through libcss (NetSurf's CSS parser and selection engine) — there is no preprocessor doing the real work, so a new property has to travel the whole pipe: **parse → computed style → select/compose → layout/redraw consumption.** Miss the last stage and the property parses fine and does nothing; the page won't error, it'll just ignore you.

Here's the journey, with the files that live at each stop. All paths are under `browser/libcss/` unless noted.

**1. Parse.** The tokens for your property have to be recognized and turned into libcss bytecode. Per-property parsers live in `src/parse/properties/` — these are the `ag_*.c` files (one per property, e.g. `ag_background_color.c`), and their prototypes plus the `property_unit_mask[]` table live in `src/parse/properties/properties.h`. The property *itself* — the `CSS_PROP_*` enum entry and the `CSS_N_PROPERTIES` count — is registered in a *different* file: the public header `include/libcss/properties.h`. Mind the two-file split: `include/libcss/properties.h` is where the enum and count live; `src/parse/properties/properties.h` is the per-property parser side. If your property has a non-trivial grammar (multiple values, shorthands), the parser under `src/parse/properties/` is where most of the real work goes.

**2. Computed style.** Once parsed, the value has to land somewhere in the computed-style structure that the cascade fills in. That structure is generated into `src/select/autogenerated_computed.h` (with a V2 variant in `autogenerated_computed_v2.h`). The getters and setters that read and write it are `src/select/autogenerated_propget.h` and `autogenerated_propset.h`. **This is the most dangerous file to touch** — see the bit-packing cautions below before you add a field here.

**3. Select and compose.** The cascade resolves which value wins, and composition merges parent and child styles for inheritance. The dispatch tables that drive this per-property are in `src/select/dispatch.c` **and** `src/select/s_dispatch.c` (the twin-file rule, below, is non-negotiable). Per-property initial / copy / compose logic lives alongside the property machinery in `src/select/properties/`. The cascade's interning of identical computed styles happens in `src/select/arena.c` — another place with a sharp edge, covered below.

**4. Layout and redraw consumption.** This is the stage people forget. A property in the computed style does nothing until the layout engine reads it and the redraw code paints it. Layout lives in `browser/netsurf/content/handlers/html/layout.c` (plus `layout_flex.c`, `layout_grid.c`); painting lives in `redraw.c` and the QuickDraw plotters at `browser/netsurf/frontends/macos9/plotters.c`. If your property is a paintable background-ish thing, note that all background painting is gated behind `html_redraw_box_has_background` in `redraw.c` — a gradient or shadow that isn't registered in that check silently no-ops on any element that has no `background-color`. That gotcha bit a real feature once; don't let it bite you.

There's one MacSurf-specific wrinkle worth knowing. The CSS handler `browser/netsurf/content/handlers/css/cssh_css.c` carries a small preprocessor that bridges a few modern standard-CSS forms (`transform`, `text-shadow`, some grid track grammar) into shapes libcss already understands. If your feature touches grid tracks, note that `cssh_css.c` has *two* track tokenizers — `macsurf__emit_grid_tracks` and `macsurf__emit_flat_tracks` (both carry the `macsurf__` prefix in the source) — and new grammar support has to be wired into **both**, or `repeat()`-and-function combinations silently emit the wrong tracks. When in doubt, the property-by-property ground truth for what's implemented versus parsed-but-dropped is [`docs/css-status.md`](https://github.com/mplsllc/macsurf/blob/master/docs/css-status.md), and the broader flow is on [The Rendering Pipeline](The-Rendering-Pipeline).

### The dispatch.c / s_dispatch.c twin rule

Both `src/select/dispatch.c` and `src/select/s_dispatch.c` define the `prop_dispatch[]` table. They exist because the file was renamed once for CodeWarrior's flat-namespace deduplication and a stale copy was later re-added — so now both live in the tree. The Mac build compiles `s_dispatch.c`; the Linux-side project references `dispatch.c`. The practical rule: **whenever you add a property to the `CSS_PROP_*` enum, edit both files, keep them byte-identical, and keep them in sync.**

The reason this matters is brutal in practice. Adding a property bumps `CSS_N_PROPERTIES` in `include/libcss/properties.h`. If you bump that count but don't update the dispatch table that the new index reads from, `set_initial` does an out-of-bounds read on the dispatch table at the new property's index. The crash signature is an unmapped-memory exception with the program counter at a garbage address and a stack trace showing `set_initial → 0xGARBAGE`. It compiles clean and dies at runtime the first time that property is exercised. Ship both files; edit both files.

### Bit-packing cautions: struct padding and arena interning

The computed-style structure is bit-packed and interned, and both of those facts will hurt you if you add a field carelessly.

**Padding.** Use `int32_t` for scalar fields in the inner `css_computed_style_i` struct, always. If you drop a `uint8_t` or `uint16_t` between two `int32_t` fields, the compiler inserts padding bytes for the next field's alignment. The cascade writes your field's bytes but nothing writes the padding, so different cascade paths can leave that padding holding different garbage. That matters because of the next point.

**Interning.** libcss deduplicates identical computed styles by doing a raw `memcmp` over the whole inner struct in `src/select/arena.c`. If two logically-equal styles differ only in unwritten padding bytes, the `memcmp` says they're different, the intern table fills with duplicates, and those duplicates get destroyed while still referenced — a use-after-free that surfaces as a crash in `css_computed_style_destroy` (often iterating the `content` array for `::before`/`::after`). The log just ends, with no "reformat" line ever firing. This exact failure mode has been hit more than once.

The rules that fall out of this:

- New fields go at the **end** of the struct, never inserted in the middle. CodeWarrior misses header-only recompiles, so a mid-struct insert shifts later fields' offsets while leaving libcss `.o` files compiled against the old layout — silent corruption mid-reformat.
- Scalar fields are `int32_t` so they self-align. No sub-`int32` scalars in `_i`.
- **Variable-size or per-cascade-divergent data must not go in `_i` at all.** Pointer fields, content arrays, and font-family lists live in the *outer* `css_computed_style` struct and get dedicated `arena__compare_*` functions registered in `css__arena_style_is_equal`, so they're compared logically rather than bit-for-bit. Follow that pattern: allocate during cascade, add a comparison function in `arena.c`, register it.
- Bit-packed flags in the `bits[N]` words are fine, because every cascade path writes the bit slot deterministically.

If a property genuinely needs more storage than this allows — a brand-new real property with its own enum and field — be aware that's not a one-round change. It touches the bit-packed struct, propset/propget, parse and select files, and the dispatch twins, and an offset miscount in any of them silently corrupts *unrelated* properties. The `row-gap`/`column-gap` shared-storage situation is documented as a deferred example of exactly this in `CLAUDE.md`. Scope it as its own pass, with a careful bit-packing audit.

## Porting a C library (the C89 audit checklist)

MacSurf's whole foundation is NetSurf's C99 libraries ported to CodeWarrior 8's strict C89, so if you bring in a new library — or update an existing one to a newer upstream — you'll run this audit. The point is to find the C99-isms before CodeWarrior does, because CodeWarrior's error messages for some of these are cryptic and cascade.

Grep every file for:

- The `inline` keyword.
- `//` line comments — both leading and trailing. Exclude URLs inside `/* */` block comments (license headers love `http://www.opensource.org/...`).
- C99 designated initializers (`.field = value`). **Count instances per file**, not files — one real-world file had 47 in it. And watch for the trap: a designated initializer for a typedef'd *union* looks identical in grep to a struct one, but C89 union initializers must be positional (`{value}`, first member only).
- For-scope declarations — integer (`for (int i ...)`) *and* the pointer-type variants (`for (TYPE *NAME = ...)`, `for (const TYPE *NAME = ...)`). The pointer forms are easy to miss and a real audit undercounted by ten sites that way.
- `restrict`, compound literals, `long long` (see the `int64_t` miscompile note in [CodeWarrior 8 & C89 Gotchas](CodeWarrior-8-and-C89-Gotchas)), variable-length arrays, flexible array members, forward enum declarations (`enum foo;` is illegal in C89), and `__attribute__` / `__builtin_*`.
- `__VA_ARGS__` variadic macros — these actually *work* in CW8 as a pre-C99 extension, but old-style fixed-param "varargs" macros don't, so know which you've got.
- `snprintf` / `vsnprintf`, and `%zu` / `%zd` printf formats.
- POSIX headers: `<iconv.h>`, `<errno.h>`, `<strings.h>`, `<sys/types.h>`, and friends.
- **GNU union casts** — `(union_type)expr` where the typedef resolves to a union. C89 forbids casting to a union type; the fix is a scoped local variable. An audit missed five of these once because `grep '(css_'` only catches them if you already know the typedef is a union.
- Build-time codegen — `gperf`, perl scripts, `.inc` files included from `.c` files. These don't run in the CodeWarrior build, so their output has to be checked in.
- Existing MacSurf stub headers in `frontends/macos9/<libname>/` that will collide with the real headers. A stub that sets the *real* header's include guard without defining its structs will silently blank out every translation unit that includes it. Stubs must use the same include guard as the header they shadow — there's a whole family of these traps in the gotchas page.

This list is maintained alongside the codebase; the canonical copy lives under "Library port audit checklist" in [`CLAUDE.md`](https://github.com/mplsllc/macsurf/blob/master/CLAUDE.md), which gets new entries whenever a fresh class of trap is found.

## The regression-audit checklist (don't ship a dead subsystem)

This checklist exists because of a real and embarrassing class of bug: a subsystem gets wired in, every commit "lands," the user tests, the maintainer tests — and the whole thing was never actually running. The file-backed debug log spent three fix rounds writing nothing because its init function was never called. A separate round had the init wired but the function body gated behind a feature macro that wasn't defined, so it compiled down to an empty stub. Both passed casual review. Neither did anything.

So before any round that adds or touches a subsystem is considered done, it has to satisfy all three:

1. **Init call wired.** Grep the entrypoint — for MacSurf that's `main()` in `browser/netsurf/frontends/macos9/main.c` — for the init function's name and confirm it's actually called. If `grep -c your_init main.c` returns zero, the subsystem is linked but dead.
2. **Init body is reachable.** If the init function's real body is behind a feature macro (`#ifdef MACSURF_DEBUG`, `#ifdef WITH_X`), confirm that macro is actually defined somewhere in the prefix file or project config. A never-defined macro means init compiles to an empty release stub and fires silently. This is the second, sneakier vector — "the init is called" is necessary but not sufficient.
3. **Smoke test that confirms it runs.** Boot the build (SheepShaver is fine for this) and confirm the subsystem's externally-visible artifact actually appears — a file written, a title-bar message, a menu item, a rendered page. "The Linux syntax check passes" is **not** a smoke test; syntax passes on code that never executes. SheepShaver caveats apply (it's more forgiving than hardware; see [Diagnostics & Debugging](Diagnostics-and-Debugging)), but for "does this subsystem fire at all" it's a 30-second answer.

If your round adds genuinely new infrastructure, add a one-line row to the regression-audit table in `CLAUDE.md` recording the init function, its call site, and the artifact you'd look for at startup. That table is how the next person verifies your subsystem is still alive after they refactor near it.

## The fix and ship workflow

MacSurf is developed on Linux and built on a Mac, so a change moves between two machines. The generic shape of a round:

1. **Edit on Linux**, then run the [Linux syntax checks](Cross-Developing-from-Linux) — Retro68 PPC GCC and `gcc -std=c89 -pedantic` with the shim paths. Fix everything they flag before going further.
2. **Convert line endings.** Source files destined for the Mac need CR (`\r`) line endings. Wiki pages and repo Markdown stay as LF — this is a Mac-source-only rule.
3. **Move the changed files to the Mac.** Any file-transfer method that preserves the data fork works (a network share, a disk image, whatever your setup uses). Move only the files you changed this round, with their full `browser/...` tree structure intact so they land in the right place. The exact transfer mechanics are a matter of your own environment.
4. **Build in CodeWarrior** on OS 9. If you added or removed `.c` files, you have to add them to the CodeWarrior project by hand through the IDE — the project doesn't autodiscover files, and a `.c` that isn't in the project compiles to nothing and links cleanly against the *old* object file, so the bug only shows up at runtime when the new code path is exercised. After file changes, "Remove Object Code" before rebuilding. Header-only changes are worse: CodeWarrior often misses them, so if old behavior persists after a header edit, touch the dependent `.c` file rather than assuming the change didn't take.
5. **Test on real hardware** for anything hardware-specific — and *especially* regression-test any change that touches redraw, layout, or libcss against a real site (mactrove.com is the usual one), not just a probe page. Probe pages don't catch real-site regressions; that's a lesson learned the hard way.

For an outside contributor going through GitHub instead of the maintainer's private workflow, the process is the ordinary fork-branch-PR flow described in [`CONTRIBUTING.md`](https://github.com/mplsllc/macsurf/blob/master/CONTRIBUTING.md): fork, branch off `master` (`fix/<issue>-...`, `feature/...`, `chore/...`), make focused commits with the project's prefix style (`fixesNNN:`, `docs:`, `chore:`), reference issues with `Closes #N` or `Refs #N`, and open the PR against `master` for manual review. CI is still being added; for now expect a human read.

## Filing issues

Issues are the public surface of the project, so the workflow is: file before you fix, link the issue from your commit, and close it on merge. The tracker is at [github.com/mplsllc/macsurf/issues](https://github.com/mplsllc/macsurf/issues), and there are templates so you don't have to guess what's useful:

- **[Bug report](https://github.com/mplsllc/macsurf/issues/new?template=bug_report.yml)** — include the OS 9 version (or SheepShaver), the hardware (model, CPU, RAM — quirks are often hardware-tied), the build (a release tag or the most recent `fixesNN` you applied), a tiny `.html` test case if you can make one, and the tail of the debug log around the failure. A five-line repro page is worth ten paragraphs of prose.
- **[Website compatibility report](https://github.com/mplsllc/macsurf/issues/new?template=compatibility_report.yml)** — for "I tried a real site and here's what happened." Positive reports matter as much as negative ones; they record what's already good enough to protect from regressions. Reports from real G3/G4 hardware are especially valued.
- **[Feature request](https://github.com/mplsllc/macsurf/issues/new?template=feature_request.yml)** — for concrete, actionable asks.

If you're looking for somewhere to start, two labels are curated for that: **[`good first issue`](https://github.com/mplsllc/macsurf/issues?q=is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22)** marks small, well-scoped tasks, and **[`help wanted`](https://github.com/mplsllc/macsurf/issues?q=is%3Aissue+is%3Aopen+label%3A%22help+wanted%22)** marks work where an extra pair of hands would actually move the roadmap. The current punch list of in-flight, deferred, and known-limitation work is in [`docs/status.md`](https://github.com/mplsllc/macsurf/blob/master/docs/status.md). Anything that isn't a reproducible bug or a concrete request — "is anyone already on X?", design ideas, show-and-tell — belongs in [Discussions](https://github.com/mplsllc/macsurf/discussions) rather than issues.

## The solo-maintainer boundary, plainly

MacSurf does something genuinely uncommon — it renders a large slice of the real web and does native TLS 1.3 on a PowerPC Mac from 1999 — and it does it as one person's spare-time project. That shapes what kind of contribution lands well:

- **Documentation PRs are welcome.** A wiki page that's wrong, a setup step that's stale, a gotcha that should be written down — those are easy yeses.
- **Well-scoped code with a real test** (a CSS test page under `tests/css/`, a hardware compatibility note, a clean C89-checked patch tied to an issue) gets a fair review.
- **The build pack is the supported artifact.** Building from a fresh clone is genuinely hard and off the supported path; the StuffIt build pack in [Building MacSurf](Building-MacSurf) is what's tested to work. Don't expect step-by-step debugging of a custom toolchain setup.
- **Reviews are best-effort.** A patch may sit for a while. That's the cost of a one-person project, not a comment on the work.

Participation is under the project's [Code of Conduct](https://github.com/mplsllc/macsurf/blob/master/CODE_OF_CONDUCT.md) (the standard Contributor Covenant). Be the kind of collaborator you'd want on a project this niche — patient, specific, and kind — and you'll fit right in.
